Clean Then Chunk

You have a folder of scraped Markdown and you want a search index a chatbot can answer from. This page explains, in plain English, what is wrong with the folder today and why splitting the work into three stages is the right plan.

What is actually in the folder

A crawler read the aem.live website and saved every page as plain Markdown text. This is the raw material.

183Pages saved
1.88MCharacters
470kTokens
0Duplicate pages
8.8kMedian page size

The good news first, because it is real. Every page arrived with its web address, its title, its description and a fingerprint, so any answer built from it can be traced back to a source. Website navigation and footers did not leak into the pages, which is the single most common thing that ruins a scraped collection. No page was saved twice. The text is clean UTF-8 with no garbled characters.

So the raw material is sound. The problem is what is mixed into it.

Three words this page uses
chunk
A small slice of a page — a few paragraphs. Search works on slices, not whole pages, because you want to hand a chatbot the relevant paragraph rather than a 70,000-character document.
token
Roughly three quarters of a word. It is how text is billed and measured. 470,000 tokens is about 350,000 words.
retrieval
Finding the right chunks for a question, then giving only those to the chatbot so it answers from your documents instead of from memory.
The problem · click a band

Two fifths of the text is not text

The website is built from blocks, and when a page is exported to Markdown those blocks come out drawn as boxes made of dashes and pipe characters. That drawing is now sitting in the middle of your sentences.

Where all 1,877,031 characters go
59.3%Real sentences
21.8%Content, drawn as boxes
18.9%Pure junk

Only the first band is ready to use. The middle band is genuine content — error code tables, card lists — but it is drawn as box art, and box art falls apart the moment you slice a page up. The last band has no value at all and should simply be deleted.

The single worst offender

Every one of the 183 pages ends with a Metadata box that spells out the page's own title and description. Your records already store the title and description as proper fields. So 14.3% of the entire collection is a restatement of two things you already have — 269,182 characters of it. That is the cheapest deletion available and nothing is lost.

The fix · pick a block

Every block gets one of three verdicts

There are 731 of these boxes across the collection. They are not all the same, and the difference matters: some hold nothing, some hold real content in an unusable shape. Click through them.

One rule keeps this safe. Delete only from a named list. Any box whose name you do not recognise gets reshaped, never deleted — because a site can add a new block type next month, and the failure you want is "a bit untidy", not "content silently vanished".

Why it matters · flip the switch

Box art breaks when you slice it

This is the part that is easy to underestimate. Deleting junk saves money. Reshaping the tables is what makes answers correct.

    Your plan · click a stage
    
Three folders, not one script

    

      Your instinct — clean into a new folder, then chunk from that — is right. Here is
      the shape, and the one wire in it that needs moving.
    


    

      

      

    

  


  


  

    The crossed-out arrow
    
Why not just read the Markdown folder?

    

      It is the obvious thing to reach for — it is a folder of readable text files,
      right there. The text in it is perfect. Everything that is not text is gone.
    


    

      The .md files begin straight at the content, with no header block. So
      the text survives the trip and nothing else does. Some of what is missing can be
      guessed at from the filename. Some cannot be recovered at any price.

Guessing the title gets it wrong 8% of the time

    

      The obvious workaround is to take the page's first heading as its title. That fails
      on 14 pages — six disagree with the real title, and eight have no heading at all.
      The failures are not near misses either, because a heading is raw Markdown and a
      title is finished text:

      Those strings become the visible source label under an answer. Stray asterisks and
      an HTML tag in a citation is the sort of thing you end up fixing later — by reading
      the file you skipped.
    


    
Two URLs cannot be recovered at all

    

      /docs/ and /developer/block-party/ end in a slash, so they
      are saved as markdown/docs/index.md. Working backwards, there is no way
      to tell whether index.md meant /docs/ or
      /docs/index. The filename convention destroyed the difference. It is
      only two pages — but it fails silently, and a silently wrong citation is worse
      than a loudly broken one.
    


    
And this is the one that actually costs money

    

      Every file in the folder was written at the same instant, because that is when the
      crawl ran. The dates the pages actually changed live only in the JSONL:
    


    

      
Distinct timestamps available from each source

      
markdown/ file timestamps    1 distinct value    2026-08-25 15:54  (when you crawled)
index lastModified          10 distinct values   2026-07-30 … 2026-08-25  (when pages changed)

      

        A file timestamp tells you when you downloaded a page. It can never tell you
        whether the page changed.
      

    


    

      Lose that column and you lose the ability to ask “which pages are new?”
      So every refresh re-cleans, re-slices and re-embeds all 183 pages
      instead of the two or three that moved. Embedding is the part you pay for. Dropping
      the metadata does not just cost you some labels — it quietly turns a cheap
      incremental pipeline into a full rebuild, every single time, forever.
    


    

      The trap, specifically
      

        The description is in the Markdown — inside the Metadata
        box, which is the very first thing stage 2 deletes. Clean from the folder and you
        destroy the only copy of the description you had, in the same pass that was
        supposed to be tidying up.
      

    


    
So what is the folder for?

    

      You. Not the pipeline. It exists so you can grep the corpus for a phrase, open one
      page and read it, and diff what the cleaner changed — none of which you want to
      do through a JSON parser. That is a genuinely useful job and it should keep doing it.
    

    

      The rule is just this: dataset.jsonl is the source of record,
      because it is the only place where the text and its metadata are guaranteed to be in
      step. The Markdown folder is a view of one column of it.
    

  


  


  

    The reasoning
    
Why the split earns its keep


    

      It would be simpler to write one script that reads the raw folder and writes chunks.
      Don't. The two halves of that script change at completely different rates.
    

    

      Cleaning is settled work. There is one correct answer to "should this
      metadata box be deleted", you will find it once, and you will never revisit it.
      Chunking is unsettled work. How big should a slice be? Should the FAQ
      split per question? Should the breadcrumb go inside the text that gets searched? You
      will change your mind about every one of those, repeatedly, based on whether answers
      come out right.
    

    

      Fuse them and every chunking experiment re-runs the cleaning. It goes from a
      two-second job to a slow one, and slow experiments are experiments you stop running.
      Keep them apart and stage 3 rebuilds in seconds from a local file, forever.
    


    

      One rule that protects the whole thing
      

        Stage 1 is read-only. Never write back into it. The crawler decides
        what to re-download by comparing a fingerprint of the text it fetched last time. If
        cleaning overwrites that text, the fingerprints stop matching and the next refresh
        re-downloads all 183 pages instead of the two that changed. Fingerprint the raw
        bytes; clean downstream.
      

    

  


  


  

    Two corrections
    
Where your plan needs a nudge


    
    
      
  1. 
        
    
          
    Read the JSONL, not the Markdown folder
    
          
    
            The text in the folder is perfect — and it is the only thing in there.
            No URL, no title, no description, and above all no date, which is what makes
            re-indexing cheap. Read the JSONL and every field rides along for free. The
            section above works through exactly what breaks if you don't.
          
    
        
    
      
    2. 
      
  2. 
        
    
          
    Make the chunks one file, not a folder of files
    
          
    
            A chunk needs to say which page it came from and which version of that page.
            That is how you re-index one changed page instead of all 320 chunks. A filename
            cannot express that; a field can. One chunks.jsonl, each line
            carrying a chunk id, a page id and the page's fingerprint.
          
    
        
    
      
    3. 
      
  3. 
        
    
          
    Harvest the anchors before you delete the boxes
    
          
    
            Those Section Metadata boxes you are about to bin contain the real
            page anchors — id: ssg, id: fast. Pull the value out
            as you drop the box and your citation becomes
            /docs/faq#ssg, which lands the reader on the exact answer instead
            of the top of a 70,000-character page. Delete the box, keep the anchor.

    Order of work
    
What to build first

    
    
      
  1. Delete the three junk block types
    Metadata, Section Metadata, Pagination. Recovers 18.9% for almost no effort and cannot break anything, because none of it was content.
    2. 
      
  2. Flatten the content tables to sentences
    One line per row, headings repeated into the line. This is the change that fixes error-code lookups, and the one worth writing tests for.
    3. 
      
  3. Record each page's heading list
    Just a list of headings with their positions. Stage 3 then slices with a simple loop instead of re-parsing Markdown, and breadcrumbs come free.
    4. 
      
  4. Print a report and make it a gate
    Junk percentage, sentence percentage, what got dropped. Fail the run if junk jumps — that is how you notice the website changed its blocks under you.
    5. 
      
  5. Now chunk, and expect to redo it
    Cut on headings, force-split the FAQ, put breadcrumbs in the searched text. Try a few settings. This is the stage you rebuild twenty times, which is exactly why it is last and separate.
