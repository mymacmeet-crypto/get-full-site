Architecture proposal · no code changed

One pipe, many sources

web-archiver has grown two pipelines that do the same five things in different ways. This is a plan to collapse them into one harness with a single document contract at the centre — so a new site, a new format, or a RAG index becomes a plug rather than a new pipeline.

01Where the code actually is

Measured, not estimated

Two commands exist today. bin/archive.js crawls a domain and captures each page as standalone HTML. bin/dataset.js reads an Edge Delivery query index and pulls each page as Markdown.

They feel like different programs, and in two respects they genuinely are. But run the stages side by side and most of the difference disappears: both discover a list of URLs, filter it, fetch each one, turn bytes into something worth keeping, and write a report. Only two of those five stages differ in substance.

The duplication was not laziness. dataset/source.js carries a comment explaining exactly why it could not call fetcher.js: the discovery fetcher deliberately cancels the body of any non-HTML response, which is precisely the bytes the dataset needs. That is a real incompatibility — and it is the signature of a missing abstraction, not a missing function call.

02The idea: one narrow waist

Everything upstream produces it; everything downstream consumes it

Pick one data structure — a Document — and make it the only thing that crosses the middle of the system. Sources produce Documents. Sinks consume Documents. Neither knows the other exists.

This is the trick the IP layer plays in the network stack, and it buys the same thing here: adding a source costs one adapter, not one adapter per output format. Four sources and four sinks is eight pieces to write, not sixteen.

03Four stages, four contracts

The plug points

Between source and sink sit two more stages worth naming separately, because both already exist twice and both are where site-specific behaviour lives.

The contracts matter more than the code. Note especially that a source yields references, not content — that single decision is what makes incremental refresh possible, because the version can be checked before paying for a fetch. 

// A source yields references, never content. This is the load-bearing choice:
// it lets the runtime skip a fetch entirely when the version is unchanged.
type DocRef = {
  id:      string        // stable identity, usually the URL
  url:     string
  version: string | null // lastModified | etag | hash — drives refresh
  meta:    object        // title, description, section, whatever the source knows
}

interface Source    { discover(ctx): AsyncIterable<DocRef> }
interface Policy    { admit(ref, ctx): { ok: boolean, reason?: string } }
interface Fetcher   { fetch(ref, ctx): Promise<Payload> }
interface Transform { transform(payload, ref, ctx): Promise<Document> }

// Sinks are streaming, not array-in. Today collect.js holds every record in
// memory — fine at 181 documents, not at 100,000.
interface Sink {
  open(ctx): Promise<void>
  write(doc: Document): Promise<void>
  close(): Promise<Result>
}

Two details worth arguing about now rather than later. Transforms should compose as an array ([html-to-text, normalise]), so a PDF and a web page can share the tail of the chain. And version should accept a content hash as well as a timestamp, so sources with no lastModified are not condemned to refetch forever — the gap the dataset collector has today.

04Refresh, generalised

The mechanism that makes a rerun cost 1.7 seconds

The dataset collector already does this and it is the single most valuable behaviour in the codebase: rerunning is the update, and unchanged documents are never fetched again. It is currently welded to one source. Lifting it into the runtime gives every source the same property for free — including the crawler, which has no equivalent today.

05Where RAG plugs in

A sink, not a second pipeline

This is the payoff, and the reason the waist is worth building. Retrieval does not need its own collector, its own crawler, or its own refresh logic. It needs the Document stream, and two more stages bolted to the end of it.

You deliberately left chunking out of collection, and that call holds up under this design: chunk boundaries depend on the embedding model's window and on how the retriever scores overlap, so they belong to the retrieval engine. Under a narrow waist that is not a compromise — the chunker reads the same Documents everything else does, and you can rebuild the index with different boundaries without re-fetching a single page.

The upsert by doc id detail is what makes refresh work end to end. Because a Document has a stable id and a sha256, the RAG sink can delete-then-insert the chunks for exactly the documents that changed, and drop the chunks of documents that left the site. Without a stable id, every refresh is a full re-index.

06A pipeline becomes a recipe

Where “very easily” actually comes from

Once the stages are plugs, a pipeline is configuration. Both of today's commands become recipes, and a new site becomes a file rather than a module. 

# recipes/aem-live.yml — replaces bin/dataset.js for this site
name: aem-live
source:   { type: query-index, site: https://www.aem.live }
policy:
  - noindex-column          # the publisher's own signal
  - exclude: ^/drafts/
fetch:    { type: http-text, suffix: .md }
transform: [ markdown ]
sinks:
  - { type: jsonl, path: archive/www.aem.live/dataset.jsonl }
  - { type: files, path: archive/www.aem.live/markdown }
# recipes/aem-live-pages.yml — replaces bin/archive.js for this site
name: aem-live-pages
source:   { type: sitemap-crawl, start: https://www.aem.live/, depth: 10 }
policy:   [ robots-txt, { include: ^https://www\.aem\.live/developer/ } ]
fetch:    { type: browser-capture, reveal: true }
sinks:    [ { type: files, path: archive/www.aem.live/raw-html } ]
Build this last, not first The recipe layer is the most attractive part of this plan and the easiest to get wrong. A registry and a config schema written for two pipelines will encode the wrong assumptions. Write the stages as plain modules first, wire them in JavaScript, and only introduce YAML once a third recipe exists and the shape has stopped moving.

07Getting there without a rewrite

Four phases, each one shippable on its own

Nothing below requires a big-bang migration. Both CLIs keep working throughout; each phase deletes duplication that is already proven, and stops if you decide the next phase is not worth it.

01

Extract the shared runtime

One HTTP client with retry, backoff and Retry-After handling, parameterised by whether the body is wanted. This is the fix for the comment in dataset/source.js explaining why it could not reuse fetcher.js — three implementations become one.

Ships: no behaviour change, ~200 lines deleted, both CLIs untouched externally.

02

Promote Document and the manifest

Move the record shape out of dataset/dataset.js into a shared module, add version alongside lastModified, and make the manifest generic. Point the crawler's report at it so both pipelines describe their runs the same way.

Ships: the crawler gains incremental refresh, which it does not have today.

03

Split the stages behind the existing CLIs

Refactor both commands to run Source → Policy → Fetch → Transform → Sink internally, keeping every current flag working. Sinks become streaming here, which is what lifts the ceiling above “fits in memory”.

Ships: identical CLI surface; the test suite is the proof it did not regress.

04

Add the third source, then the recipe layer

A plain URL-list source is the cheapest honest test of whether the seams are in the right place. If it drops in without touching the runtime, the abstraction holds and the recipe format is worth writing. If it does not, you have learned that for the price of one small module.

Ships: the decision on whether to go further, backed by evidence.

09What I would resist

Do not build a plugin framework. Two pipelines do not justify dynamic loading, lifecycle hooks, or a plugin API with versioning. Plain modules in a folder, imported by name, cover everything described here. Every abstraction above should be deletable in an afternoon if it turns out to be wrong.

Do not unify the two CLIs into one command. archive and dataset mean genuinely different things to whoever types them, and the ten shared flags can be shared without merging the commands. A single harness run with a mode flag would be worse for the user and no better for the code.

Do not let the waist get wide. The moment a Document grows a field that only one sink reads, the contract has started leaking, and the N + M property quietly reverts to N × M. Source-specific data has a home already — the indexFields escape hatch — and it should stay there.

Weigh the honest cost. 3,546 lines work today and are covered by 170 tests. Phase 1 pays for itself immediately. Phases 3 and 4 are worth doing only if a third source is actually coming — if aem.live is the whole job, stop after phase 2 and keep the duplication.

10What I need from you

  • Is a third source real? That single answer decides whether this stops at phase 2 or runs to phase 4.
  • Which vector store? The sink contract is the same either way, but batching and upsert semantics differ enough to matter.
  • Retrieval or training? You have said RAG; if a training corpus is also in scope, deduplication and long-document handling belong in the plan and are not there now.
  • How large does this get? Streaming sinks are phase 3 work. If the corpus stays in the low thousands, that phase can be deferred indefinitely.
